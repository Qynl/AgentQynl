# Qynl Agent V30

V30 is the **agent reliability and evaluation update**. The goal is to stop treating intelligence as a pile of modules and start treating Qynl as a measurable control system.

## Core idea

```text
OBSERVE
   ↓
UNDERSTAND
   ↓
GENERATE CANDIDATES
   ↓
DECISION GATE
   ↓
EXECUTE ONE BOUNDED ACTION
   ↓
VERIFY
   ↓
HEALTH CHECK
   ↓
LEARN / REPLAN
```

Every layer has a contract. No learned preference bypasses the decision gate or execution safety boundary.

## V30 components

### Typed contracts

`minecraft/v30_contracts.py`

Defines shared representations for:

- observations
- confidence bands
- candidate actions
- decisions
- verification results

This reduces the amount of implicit state passed between components.

### Decision Gate

`minecraft/v30_decision_gate.py`

Before an action can be selected, V30 checks:

- observation confidence
- action risk
- expected progress
- bounded action cost

If confidence is too low or every candidate fails the gate, V30 chooses **no action**. Exploration/re-observation can then take over.

This is intentionally conservative. The agent should prefer knowing that it does not know over confidently walking into lava.

### Runtime Health

`minecraft/v30_health.py`

The health monitor watches:

- loop lag
- consecutive failures
- time since the last verified result

An unhealthy runtime can be stopped or routed into recovery by the higher-level controller.

### Benchmark Harness

`minecraft/v30_benchmark.py`

V30 introduces deterministic decision benchmarks. A benchmark case contains:

- a controlled observation
- candidate actions
- expected selected action

The harness reports per-case results and an overall score.

The benchmark is deliberately separate from the live Minecraft loop. This means changes to planning logic can be measured before putting the agent into a real world.

## V23 → V24 → V26 → V30

**V23** learned from verified outcomes.

**V24** introduced a serious real-time runtime with guarded execution and telemetry.

**V26** introduced long-running mission control and bounded recovery.

**V30** adds the missing engineering layer: **explicit contracts, conservative decision gating, runtime health and repeatable benchmarks**.

## Real gameplay workflow

1. Run deterministic benchmarks.
2. Start Minecraft in a dedicated test world.
3. Run Qynl in dry-run mode.
4. Verify perception and mission state.
5. Verify Force ESC and watchdog.
6. Run short missions.
7. Inspect health and verification data.
8. Only then enable real input.
9. Compare live failures against benchmark results.
10. Fix the measured failure before increasing mission difficulty.

## Safety boundary

```text
Model / memory / learning
            ↓
      Candidate actions
            ↓
       Decision Gate
            ↓
        ActionPolicy
            ↓
       Rate Limiter
            ↓
        Watchdog
            ↓
     Guarded Executor
            ↓
        Force ESC
            ↓
         Minecraft
```

The decision gate does not replace the existing safety stack. It adds another layer before execution.

## What V30 actually improves

V30 is intentionally less about adding another model and more about making the existing system falsifiable.

Instead of:

```text
"The AI feels smarter."
```

we can now ask:

```text
Did perception confidence pass?
Did the candidate pass the risk gate?
Which action was selected?
Was the result verified?
Was the runtime healthy?
Did the benchmark score improve?
Did the mission complete?
```

That is the foundation required for serious iteration.

## Limitations

V30 does not claim that Qynl can already solve arbitrary Minecraft tasks autonomously. The benchmark harness measures the decision layer, not the entire physical game loop. Real-world reliability still depends on the actual vision model, Minecraft input adapter, model latency, verification quality and environment.
