# Qynl Agent V3

V3 turns the safety architecture into an explicit **deny-by-default action boundary** between the AI and Minecraft input.

## Core change

The model produces a structured `MinecraftAction`. It never gets direct access to the keyboard, mouse, shell, or operating system.

```text
Model
  ↓
Proposed MinecraftAction
  ↓
ActionPolicy
  ├── allowlist
  ├── bounds
  ├── duration limits
  └── type validation
  ↓
Force ESC checkpoint
  ↓
Optional approval
  ↓
Minecraft executor
```

Anything not explicitly allowed is rejected.

## V3 action policy

The first policy layer supports a small Minecraft-oriented action vocabulary:

- allowlisted movement/game keys
- bounded mouse movement
- left/right mouse input
- bounded waits

The policy intentionally does not expose arbitrary key codes, arbitrary OS mouse coordinates, shell commands, process launching, or filesystem operations.

The policy is validation only. A real executor must still check the Force ESC latch immediately before sending input.

## Force ESC

Force ESC remains an operator-only hard stop. It is outside the model's tool registry and cannot be requested by model output.

The intended executor sequence is:

```text
validate action
→ check Force ESC
→ check approval state
→ execute
→ return outcome
```

If Force ESC is engaged, no new Minecraft input should be sent.
