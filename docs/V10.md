# Qynl V10 - Functional Minecraft Agent

V10 is the first release that wires the full gameplay path into one runnable Python agent instead of leaving the model connection as a future task.

## What is actually connected

```text
Minecraft window
      ↓
MSS capture → PNG frame
      ↓
Multimodal vision model
      ↓
VisualAnalysis
      ↓
Goal context
      ↓
Multimodal planner
      ↓
strict MinecraftAction parser
      ↓
ActionPolicy
      ↓
Force ESC
      ↓
PyAutoGUI Minecraft input
      ↓
Minecraft
      ↓
next frame
```

`minecraft/run_v10.py` runs this loop continuously.

## Providers

V10 uses one small OpenAI-compatible HTTP transport. This means the same agent can target:

- NVIDIA NIM
- local Ollama OpenAI-compatible endpoints
- another compatible multimodal endpoint

Provider-specific URLs and credentials come from environment variables. The provider only receives the Minecraft image and Minecraft task context.

### NIM

Set:

```text
QYNL_PROVIDER=nim
NVIDIA_API_KEY=...
QYNL_MODEL=<vision-capable-NIM-model>
QYNL_BASE_URL=<NIM-compatible-base-url>
```

### Ollama

Run a vision-capable model locally, then:

```text
QYNL_PROVIDER=ollama
QYNL_BASE_URL=http://127.0.0.1:11434/v1
QYNL_MODEL=<installed-vision-model>
```

## Capture

Configure the Minecraft window rectangle:

```text
QYNL_CAPTURE_LEFT=0
QYNL_CAPTURE_TOP=0
QYNL_CAPTURE_WIDTH=1280
QYNL_CAPTURE_HEIGHT=720
```

The capture adapter writes only the configured Minecraft region to `QYNL_CAPTURE_DIR`.

## Run safely first

```text
QYNL_DRY_RUN=1
QYNL_ONCE=1
python -m minecraft.run_v10
```

This performs real capture and model reasoning but does not send keyboard/mouse input.

## Enable real input

After verifying the capture region, model output, ActionPolicy and Force ESC in a dedicated Minecraft test world:

```text
QYNL_DRY_RUN=0
python -m minecraft.run_v10
```

The model still cannot send arbitrary OS input. Every proposed action is parsed into the canonical `MinecraftAction` and checked by `ActionPolicy` immediately before execution.

## Model output contract

The planner must return exactly one action:

```json
{"type":"key","key":"w","duration_ms":250}
```

```json
{"type":"mouse_move","x":35,"y":-8}
```

```json
{"type":"mouse_button","button":"left","duration_ms":80}
```

```json
{"type":"wait","duration_ms":150}
```

Anything else is rejected.

## Why V10 is different

Earlier versions had the pieces separately. V10 connects the pieces into an actual closed loop and fixes the action-schema mismatch between the policy and the real input adapter.

It is still a model-driven system, so gameplay quality depends heavily on the chosen vision model, latency, capture framing, and prompt/model capability. The code path itself no longer depends on an imaginary future provider adapter.

## Safety

- Force ESC is independent of the model.
- Real input is opt-in.
- The default is dry-run.
- Actions are allowlisted and bounded.
- Provider output is treated as untrusted JSON data.
- No shell, process, filesystem, or arbitrary desktop tool is exposed.
- Use a dedicated Minecraft test world/account when experimenting.
